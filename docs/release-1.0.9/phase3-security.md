# Wavelength 1.0.9, Phase 3: encrypted backups, app lock and local data protection

8 October 2026. Tests: dummy accounts and generated bytes only, never patient data.

## 1. What changed

| Area | 1.0.8 | 1.0.9 |
|---|---|---|
| Backup file | Unencrypted stored ZIP (`.zip`), built whole in memory | Encrypted `.wlbackup` (AES-256-GCM, Argon2id), written as a stream |
| Backup screen | Yellow warning card on Home | "Back up and restore" screen (Me and Settings), calm reminder card on Home |
| Restore | Unzip in memory, no integrity check | Each 1 MiB chunk verified before use, SHA-256 per photo or clip, no duplicates |
| Old ZIP backups | Restored | Still restored, after a warning to replace them with an encrypted backup |
| App lock (Android 11+) | Plugin default: any biometric, weak face unlock included | Strong (Class 3) biometrics or the phone's PIN, pattern or password, one system prompt |
| App lock (Android 7 to 10) | Any biometric | Strong biometrics only; the lock can be turned on only when the phone has one |
| App lock (iPhone) | Face ID or Touch ID with passcode | Unchanged |

## 2. Backup design (approved: "Argon2id, built-in", Fero, 8 October 2026)

Full byte layout: [docs/backup-format.md](../backup-format.md).

- **Cipher:** AES-256-GCM from the platform's Web Crypto (Android System WebView, iOS WebKit), 1 MiB chunks, the
  header as additional data, nonce = random 7-byte prefix, chunk counter and last-chunk flag (STREAM construction).
  Detects any changed byte, reordered or missing chunks, truncation and appended data.
- **Key derivation:** Argon2id, 64 MiB, 3 passes, 1 lane, 16-byte random salt, then HKDF-SHA256 to the AES key.
  Argon2id comes from `@noble/hashes` 2.4.0 (MIT, widely used), vendored unchanged in
  `src/app/vendor/noble-hashes/` and loaded only when a backup is made or restored. The library's 2022 Cure53 audit
  covered its other hashes but **not argon2**, so correctness is checked here instead: it matches the RFC 9106 test
  vector, and every test run has OpenSSL's independent Argon2id (through Python `cryptography`) decrypt an app-made
  file. Argon2id output only feeds HKDF and AES-GCM from Web Crypto, so a flaw in it could weaken guessing
  resistance but could not leak plaintext.
  About 2 s in headless Chromium on a laptop; expect 3 to 8 s on a mid-range phone (to measure on the physical device).
- **No custom cryptography.** `backup.js` only frames chunks. A second, independent reader in Python
  (`tools/backup-decrypt.py`, the `cryptography` package) decrypts app-made files in the test suite, so a backup does
  not depend on the app alone.
- **Passphrase:** at least 10 characters, typed twice, NFC-normalised, never stored or sent. The learner must tick
  "Wavelength cannot recover a forgotten passphrase". No recovery key exists by design.
- **No unencrypted temporary files.** Plaintext exists only in memory, one image or clip at a time. On the phone,
  ciphertext is appended to `Cache/backup/<name>.wlbackup` and handed to the share sheet; the folder is emptied at the
  start of the next backup. On the website the ciphertext is held in a Blob until downloaded. Restore streams the
  chosen file a chunk at a time and writes only verified data into IndexedDB.
- **Hostile files:** cost parameters are bounded before any work (Argon2id at most 256 MiB, 10 passes), so a crafted
  file cannot exhaust the phone.
- **Duplicate-safe restore:** entries already present are kept, photos and clips with an existing id are skipped,
  each restored file is checked against its SHA-256, and restored entries sync as restored copies (a newer server
  copy wins). Restoring the same file twice adds nothing (browser check B8).
- **Honest status:** the success sheet says "Encrypted backup created" only after the last chunk is written, then
  asks the learner to save it with the share sheet; Wavelength cannot see where it was saved, so it never says
  "backed up to the cloud". The screen does not claim that Google Drive, OneDrive or iCloud give app-only access or
  end-to-end encryption, and makes no NHS or UK GDPR claim. It says: "The file stays encrypted wherever you keep it,
  and whoever can open that storage can copy the file but not read it without the passphrase."

### Options considered (for the record)

| | A. Argon2id, built in (chosen) | B. Argon2id via WebAssembly (hash-wasm) | C. PBKDF2-SHA256 |
|---|---|---|---|
| Speed (64 MiB) | ~1.4 s Node, ~2 s Chromium | ~0.4 s | 600,000 iterations ~0.5 s |
| Resistance to GPU guessing | Strong (memory-hard) | Same files as A | Weaker |
| Content Security Policy | Unchanged | Needs `'wasm-unsafe-eval'` | Unchanged |
| Extra code | 6 small JS files | WASM blob | None (Web Crypto) |

A and B produce byte-identical files, so a later switch to B needs no format change. The format also accepts PBKDF2
(id 2) so a future platform without Argon2id can still write readable files.

### Tests

- `test/backup-format.test.mjs`, 12 tests: RFC 9106 vector, default cost, round trips (0 B to 2.5 MiB, exact chunk
  multiples), fresh salt and nonces, wrong passphrase, tampering (salt, nonce, body, tag), truncation at and inside a
  chunk, appended bytes, swapped chunks, nothing released before verification, version and cost limits, PBKDF2,
  NFC, Python interop, streaming ZIP with CRC checks.
- `tools/e2e-backup.mjs`, 11 checks on three stand-in phones with the real bundle: short passphrase refused, file
  created, file encrypted (no dummy note text or file names, 64 MiB Argon2id in the header), file decrypts to the logbook and media, Home card,
  wrong passphrase, restore on a second phone, double restore with no duplicates, changed file refused, old ZIP
  restores after the warning, junk file refused. Results: `phase3-e2e-backup.json` (11/11, run twice).

## 3. App lock

- Uses only the operating system's prompt (Android BiometricPrompt, iOS LocalAuthentication) through
  `@capgo/capacitor-native-biometric` 8.7.0. Wavelength never sees a fingerprint or face, has no camera-based
  identification and needs no network (unit test asserts no request is made).
- **Android 11+:** `allowedBiometryTypes [3, 7]`, which the plugin maps to `BIOMETRIC_STRONG | DEVICE_CREDENTIAL`
  (`BiometricAuthenticatorConfig.java`). Class 2 (weak) face unlock is not accepted. The PIN, pattern or password is
  offered in the same prompt.
- **Android 7 to 10:** Android cannot combine strong biometrics with the screen lock in one prompt there, so the prompt
  is `BIOMETRIC_STRONG` only and the lock can be switched on only when `isAvailable` reports strength 1 (strong). A
  phone with only weak face unlock cannot turn the lock on, and a lock already on is switched off at the next
  launch with "App lock is off: this phone has no fingerprint or face unlock set up".
- **iPhone:** `deviceOwnerAuthentication` (Face ID or Touch ID, passcode fallback), unchanged.
- **Enrolment changes:** the lock is a gate in front of the app, not a key: each unlock asks the system prompt, which
  accepts whatever strong biometrics are enrolled at that moment. Enrolling a new fingerprint already requires the
  phone's PIN, pattern or password, which the prompt accepts anyway, so a new enrolment gives no extra access. A
  Keystore key bound to biometrics with `setInvalidatedByBiometricEnrollment` would need native code and would sign
  the learner out on every enrolment change; not done in 1.0.9 (listed as an option in outstanding issues).
- **Removed screen lock:** if the phone's screen lock is removed, `lockAvailable()` returns false and the app turns
  the lock off with a message rather than locking the learner out; the logbook stays on the device.
- A failed or cancelled prompt never unlocks (`test/biometric.test.mjs`, 5 tests).

## 4. Local data protection (review, no changes needed in 1.0.9)

- **At rest:** logbook entries, photos and clips are in the WebView's IndexedDB inside the app sandbox. Android 10+
  phones use file-based encryption (credential-encrypted storage, unreadable until first unlock after boot). iOS
  WebKit data has Data Protection class "complete until first user authentication" by default. Wavelength adds no
  database-level encryption of its own; doing so would need a key held in the Keystore or Keychain and native
  storage, and would not protect against someone who has the unlocked phone and app. Recommended later, with native
  image storage on iOS.
- **Login token:** stored through the biometric plugin's `setData` (Android: AES key in AndroidKeyStore, ciphertext
  in app-private SharedPreferences; iOS: Keychain), never in Preferences or localStorage. It is not bound to the
  biometric prompt, so the app lock gates the interface, not the token.
- **OS backups:** Android `allowBackup="false"`, `fullBackupContent="false"` and `data_extraction_rules.xml`
  excluding every domain from cloud backup and device-to-device transfer. iOS excludes `Library/WebKit` from iCloud
  and computer backups on every launch (`excludeWebKitFromBackup`, applied by `mobile/scripts/patch-native.py`).
  Clinical media therefore never leave the phone automatically; a new phone gets them back only from the learner's
  own encrypted backup. No automatic upload of clinical media was added.
- **Recents screenshot:** Android and iOS show a snapshot of the last screen in the app switcher. `FLAG_SECURE`
  (Android) and a privacy cover on `applicationWillResignActive` (iOS) would hide it, but `FLAG_SECURE` also blocks
  the learner's own screenshots. Recommended as a setting tied to the app lock in a later release; not changed now.
- **Legacy ZIPs:** old unencrypted backups the learner saved elsewhere remain readable by anyone with that storage.
  The app warns on restore and asks the learner to replace and delete them; it cannot delete them itself.

## 5. Upgrade from 1.0.8

No storage migration: IndexedDB version unchanged (2), token key unchanged (`wavelength.session`), `wl-lock`
preference unchanged. A learner with the app lock already on keeps it; on Android 11+ the next prompt simply also
offers the PIN, and weak face unlock stops being offered. On Android 7 to 10 with only weak face unlock, the lock is
switched off with a message at the next launch instead of locking the learner out. To verify on the physical phone
(Phase 5 checklist).
